## Treat Review as Shared Problem Solving

Maintainers balance contributions against release plans, compatibility, support cost, and available time. A technically valid patch may still need a different approach or may not fit the project’s scope.

Respond to feedback with a revision or a clear explanation. Ask focused questions when requirements are unclear. Keep the discussion on the issue or pull request so later contributors can find the reasoning. Follow the project’s communication guidance and avoid repeated requests for an immediate response.

If you can no longer continue, say so and leave the branch in an understandable state. If the change is accepted, read the final patch and release information. Merging does not guarantee immediate publication in a released version.

Track follow-up bugs you discover and credit others’ work according to project conventions. Do not copy code between projects without checking the license and attribution requirements.

## Final Practice

Write a response to a maintainer who asks for a regression test and a narrower patch. **Check:** identify the failing scenario, remove unrelated changes, report the check results, and explain any remaining limitation without turning the discussion into a defense of the original draft.
